# AI 剪辑工作台落地实施计划

## 0. 文档目的

本文档把“配置参数 -> 自动生成项目 -> 分镜渐进进入时间线 -> 自动生成初稿 -> 用户微调 -> 手动导出”拆成可以分阶段交付的实施任务。

本文档面向负责实际改代码的 GPT-5.6 Sol Medium 或同等能力工程模型。每个阶段都是一个独立交付单元：完成实现、测试和验收后必须停止，等待产品负责人确认，不能自动进入下一阶段。

本轮只定义实施计划，不修改业务代码。

## 1. 最终产品定义

### 1.1 两个明确入口

快捷创作保留两个入口，避免一个按钮同时表达两种相反意图：

1. `生成初稿并打开工作台`：创建项目、自动开始生成、打开工作台、自动生成一版初稿视频；用户随后可以继续修改并手动导出。
2. `仅生成成片`：沿用现有快速生成路径，不创建或打开编辑工作台，适合不需要精修的用户。

默认主按钮使用第一个入口；第二个入口保留为次要按钮。

### 1.2 项目和导出的关系

项目是用户持续编辑的可变工作稿；导出是项目某一时刻的不可变结果。

```text
Project（可变工作稿）
  ├─ Scene 顺序、旁白、提示词、停留时长
  ├─ 当前素材版本、候选素材版本
  └─ 当前配乐和字幕配置

GenerationRun（一次素材生成运行的不可变计划）
  └─ 负责补齐 TTS 和画面素材，不直接代表最终视频

ExportRevision（某一时刻的不可变导出输入）
  ├─ 场景顺序和时长
  ├─ 当前素材版本和音频
  ├─ BGM、字幕、模板等配置
  └─ 输出视频状态和路径
```

自动生成的第一版视频也是一个 `ExportRevision`，但标记为初稿。用户之后修改项目时，初稿文件不被覆盖；手动导出会创建新的 `ExportRevision`。

### 1.3 P0 支持范围

首个可交付版本只支持当前项目最匹配的 AI 分镜场景：

- 1 个项目包含 1-100 个分镜。
- 每个分镜包含一张当前图片、一个旁白音频和由音频驱动的基础时长。
- 分镜可以调整顺序。
- 分镜可以延长画面停留，但不能短于旁白音频时长。
- 分镜可以修改旁白、提示词、当前图片和候选图片。
- 项目级可以修改 BGM、BGM 音量以及现有导出配置中已经支持的字段。
- 生成完成后自动导出一版初稿。
- 用户可以在工作台中修改后手动导出。
- 继续使用现有 FastAPI、SQLite、本地项目媒体目录和 FFmpeg 生成链路。

### 1.4 明确不在本计划首期实现

以下内容不能在实现过程中被“顺手”加入：

- 完整多轨 NLE。
- 任意 MP4 片段的入点/出点裁剪。
- 转场、滤镜、关键帧、速度曲线和任意画面叠加。
- 跨项目素材库。
- 实时多人协作。
- WebSocket/SSE 推送。
- 浏览器端 `ffmpeg.wasm` 合成。
- 为了引入完整开源编辑器而重写现有项目模型。

如果实际验收确认“每个分镜必须是独立 MP4 视频片段”，必须在阶段 1 的闸门处暂停并重新确认媒体模型，不得直接把图片字段改成视频路径后继续开发。

## 2. 当前代码基线

实施时以仓库当前代码为准，并保留工作区中已有的用户修改。不要使用破坏性 Git 操作，不要回滚不属于本阶段的文件。

### 2.1 已有能力

- `frontend/src/components/QuickCreate.tsx` 已区分直接生成和进入工作台。
- `frontend/src/components/ProjectWorkbench.tsx` 已提供工作台布局、项目加载、运行轮询、场景检查器、时间线、任务队列和导出入口。
- `api/routers/projects.py` 已提供项目、场景、素材版本、生成运行、时间线和导出接口。
- `pixelle_video/models/workbench.py` 已定义 `Project`、`Scene`、`AssetVersion`、`GenerationRun`、`GenerationRunItem` 和 `ExportRevision`。
- `pixelle_video/services/workbench_repository.py` 已提供 SQLite 持久化。
- `pixelle_video/services/project_generation_service.py` 已提供按场景执行 TTS -> 图片、失败继续、暂停、取消、恢复和失败重试。
- `pixelle_video/services/workbench_jobs.py` 已提供 TTS、图片素材和导出任务入口。
- `frontend/src/components/WorkbenchTimeline.tsx` 已支持场景顺序和额外停留时长。

### 2.2 必须先承认的实现缺口

1. 创建项目后目前还需要用户再次点击 `开始生成`，没有完成真正的一键启动。
2. 工作台当前是卡片式轻量时间线，没有播放头、波形、拖拽剪切或完整多轨。
3. 当前工作台素材流程是图片 + 音频；图片生成和图片上传逻辑不能直接代表 MP4 视频片段。
4. 项目配置虽然保存了 BGM 等参数，但工作台目前缺少项目级配置修改接口和 UI。
5. 导出任务传入了 `existing_scene_assets`，但必须用测试确认下游 pipeline 是否真的消费这些素材；不能假设导出不会重复调用 AI 生成。
6. 导出快照中的 `durationSeconds` 和 `manualHoldSeconds` 必须通过实际输出测试确认确实影响 FFmpeg 合成，而不能只确认字段已经写入 SQLite。

## 3. 不可破坏的业务不变量

所有阶段都必须遵守以下规则：

1. `GenerationRun.parameter_snapshot` 在运行创建后不可变。用户在生成中修改项目配置，只影响下一次运行或导出，不影响当前运行。
2. 同一项目最多存在一个非终态 `GenerationRun`。
3. 生成运行使用创建时的场景顺序、旁白和提示词快照；等待中的场景修改不回写当前运行计划。
4. 当前素材版本和候选版本分离。新生成结果有当前版本时只能成为候选，不能静默替换当前版本。
5. 当前场景正在生成时锁定该场景；其他场景仍可编辑。
6. 音频时长是分镜最小时长。任何保存后的有效时长必须满足：`effective_duration >= audio_duration`。
7. 手动延长停留不重新生成 TTS 或图片。
8. 修改 BGM、字幕、顺序或停留时长不重新生成 AI 素材，只使项目产生未导出修改。
9. `ExportRevision` 创建后不得被项目后续编辑改变。
10. 初稿导出失败不能污染项目状态；保留失败的 `ExportRevision` 和可读错误，允许重试。
11. 任何媒体输出必须保存在项目目录内，数据库只保存项目内相对路径。
12. 生成失败只影响对应分镜；后续分镜继续执行，失败项可以单独重试。

## 4. 总体实施顺序

实施拆成 5 个阶段。每个阶段完成后都必须执行本阶段验收，并在报告中说明：修改文件、测试命令、测试结果、未解决问题和是否满足闸门条件。报告完成后停止，等待用户确认。

| 阶段 | 名称 | 主要交付 | 完成后状态 |
|---|---|---|---|
| 1 | 契约冻结与导出素材复用 | 明确模型、配置更新、初稿导出契约，打通或证明素材复用 | 可以安全开始自动初稿流程 |
| 2 | 一键生成与初稿自动导出 | 创建项目后自动启动运行，时间线渐进回填，完成后导出初稿 | 一次点击得到项目、初稿和可恢复运行 |
| 3 | P0 工作台编辑闭环 | BGM/项目设置、顺序、停留、候选、脏状态和手动导出 | 用户可以修改后导出最终版本 |
| 4 | 轻量时间线和预览增强 | 稳定的播放、选中、拖拽停留和场景预览体验 | 工作台可用于重复日常精修 |
| 5 | 完整验收与上线准备 | 回归、恢复、失败、性能、浏览器和许可证检查 | 可以决定上线或进入下一期 |

# 阶段 1：契约冻结与导出素材复用

## 1.1 阶段目标

在不改变用户入口的前提下，先把后续所有阶段依赖的项目配置、导出快照、初稿标识和素材复用契约固定下来。这个阶段不追求完整 UI，重点是避免后续生成和编辑使用两套互相覆盖的数据。

完成后必须能用测试证明：导出使用当前项目素材和配置快照，不会因为导出而重复调用 TTS、图片生成或外部媒体供应商。

## 1.2 预计涉及文件

优先复用现有文件，只有需要时才新增文件：

- `pixelle_video/models/workbench.py`
- `pixelle_video/services/workbench_repository.py`
- `pixelle_video/services/workbench_generation.py`
- `pixelle_video/services/workbench_jobs.py`
- `pixelle_video/services/project_generation_service.py`
- `api/schemas/workbench.py`
- `api/routers/projects.py`
- `frontend/src/types.ts`
- `frontend/src/lib/workbenchApi.ts`
- `tests/` 下对应的 workbench/repository/API 测试

不要在本阶段引入完整开源编辑器或新的时间线依赖。

## 1.3 数据契约

### Project

保留现有字段，并补充能够表达编辑状态和最近导出的只读信息。推荐响应增加：

```text
latestExport:
  exportId: string | null
  purpose: "initial" | "manual" | null
  status: "pending" | "running" | "completed" | "failed" | "cancelled" | null
  outputUrl: string | null
  createdAt: string | null
  updatedAt: string | null

dirty: boolean
```

`dirty` 的计算必须由后端完成，不能由前端凭猜测计算。推荐以项目可变版本号或 `updated_at` 与最近成功导出快照时间比较；如果使用时间比较，必须处理同一时间戳精度问题。

### Project 配置更新

增加一个项目级更新接口：

```text
PATCH /api/projects/{project_id}

请求：
{
  "title": "可选",
  "config": { "完整的当前项目配置" },
  "expectedUpdatedAt": "可选的并发校验时间戳"
}
```

第一版可以只支持完整 `config` 替换，不要同时实现复杂 JSON Patch。服务端必须：

- 校验项目存在。
- 只允许白名单配置字段。
- 保留不属于编辑器的系统配置，不允许前端覆盖服务端密钥或路径。
- 更新项目 `updated_at`。
- 不改变活动 `GenerationRun.parameter_snapshot`。
- 返回最新项目响应。

如果使用 `expectedUpdatedAt`，冲突返回 `409`，前端重新拉取项目后再决定是否覆盖。不要静默覆盖运行中任务或用户刚保存的内容。

### ExportRevision

快照内部至少包含：

```text
projectId
purpose: "initial" | "manual"
sceneOrder: string[]
scenes: [
  {
    sceneId
    position
    durationSeconds
    manualHoldSeconds
    versionId
    imagePath
    audioPath
  }
]
config
allowIncomplete
createdFromRunId: string | null
```

`purpose`、`createdFromRunId` 可以先放在 `snapshot` 中，除非查询和索引确实需要独立数据库列。遵循最小改动原则。

## 1.4 素材复用实施要求

先追踪现有 `core.generate_video` 到实际 pipeline、`frame_processor` 和 FFmpeg 合成位置，确认以下问题：

1. 现有 pipeline 是否能从传入的图片和音频直接进入合成阶段。
2. `existing_scene_assets` 是否会被消费。
3. 模板、字幕、BGM、motion 和画布配置是否能在不重新生成素材的情况下复用。
4. `durationSeconds` 和 `manualHoldSeconds` 是否实际影响合成。

实现时只选择一个共享入口修复复用逻辑，禁止在每个 pipeline 中分别复制一套导出代码。优先顺序：

1. 复用现有的 asset-reuse/storyboard 路径。
2. 如果现有路径无法接收项目素材，在公共 pipeline context 中增加已有素材映射。
3. 只有现有管线无法安全复用时，才新增一个小型“项目快照合成适配器”，继续调用已有 FFmpeg/template/subtitle/BGM 服务。

无论采用哪种方式，都不能在导出阶段再次调用 `core.media` 或 `core.tts` 来生成同一场景的素材。

## 1.5 阶段测试

至少增加或补齐以下测试：

- 项目配置更新成功并持久化。
- 非白名单配置不会覆盖服务端配置。
- 活动生成运行的参数快照不会被项目配置更新修改。
- 导出快照包含场景顺序、时长、当前版本、音频和当前 BGM 配置。
- 生成一个包含图片和音频的项目后导出，mock 的 TTS、图片和媒体 provider 调用次数为 0。
- 导出快照创建后修改项目，旧快照内容不变。
- 修改 `manualHoldSeconds` 后实际导出时长增加；不能短于旁白音频。
- 缺少素材时默认阻止导出；允许不完整导出时只按现有规则处理并记录警告。

## 1.6 阶段 1 闸门

只有以下条件全部满足，才能进入阶段 2：

- 项目配置更新 API 和 schema 已稳定。
- 自动初稿和手动导出共用同一套 `ExportRevision` 快照结构。
- 导出不会重复调用 AI 素材生成。
- 手动停留时长在最终视频中真实生效。
- 现有历史任务项目和直接生成路径没有回归失败。
- 所有新增/修改测试通过。

完成后停下来，等待产品负责人确认。

# 阶段 2：一键生成与初稿自动导出

## 2.1 阶段目标

把快捷创作的主入口改为一次点击完成：创建项目、自动启动 `GenerationRun`、打开工作台、分镜渐进回填，并在运行成功后自动导出一版初稿。

直接生成路径保持独立，不创建工作台项目，不改变原有用户意图。

## 2.2 后端执行规则

沿用现有 `ProjectGenerationService`，不要重写整个调度器。

在运行终态处理时增加初稿导出判断：

```text
GenerationRun completed
  ├─ 有失败项 → 不自动导出，显示“仅重试失败项”
  ├─ 有缺失素材 → 不自动导出，显示阻塞分镜
  └─ 全部素材可用 → 创建 purpose=initial 的 ExportRevision
                         ↓
                     启动导出任务
```

候选图片不阻止初稿导出。只要每个场景有当前版本，就使用当前版本；候选版本仍需用户显式确认。

自动导出必须幂等：

- 同一 `run_id` 最多创建一个初稿导出。
- API 重启恢复运行时不能重复创建初稿。
- 导出任务重试要重用原 `ExportRevision`，不能重新读取当前项目生成不同输入。
- 用户在初稿导出期间继续修改项目，不改变正在导出的文件。

推荐在 `ExportRevision.snapshot` 中保存 `createdFromRunId`，并在 repository 中提供按项目和运行查询的方法；如果已有唯一约束模式，优先复用已有数据库风格。

## 2.3 前端入口改造

### QuickCreate

在 `frontend/src/components/QuickCreate.tsx` 中：

- 主按钮文案改为 `生成初稿并打开工作台`。
- 次要按钮文案改为 `仅生成成片`。
- 主按钮提交时继续创建项目，但成功后必须自动启动生成运行。
- 如果创建项目成功、启动运行失败，项目不能丢失；切换到工作台并显示可重试错误。
- 提交锁、配置核对和幂等键继续保留。

### App

在 `frontend/src/App.tsx` 中：

- `handleCreateProject` 完成创建项目后调用 `startGenerationRun(projectId)`。
- 只有创建成功后才切换到 `project-workbench`，避免无项目时打开空工作台。
- 如果返回活动运行冲突，读取并显示已有运行，而不是再次提交。
- 直接生成 `handleGenerateTask` 不调用项目接口。

如果后续发现前端串联两个请求会导致明显竞态，再考虑增加后端 `POST /api/projects?startGeneration=true`；阶段 2 首选先复用现有两个接口，避免新增重复协议。

## 2.4 工作台渐进回填

工作台打开后应立即显示全部场景占位，不能等待所有素材生成完成才显示时间线。

每个场景保持稳定尺寸和位置：

1. 初始状态显示编号、旁白摘要、`待生成`。
2. TTS 完成后显示真实音频时长，时间线片段可以从占位宽度切换到真实宽度，但不能导致其他片段数据顺序改变。
3. 图片完成后显示当前图片缩略图。
4. 已有当前图片时，新图显示为候选，不替换当前画面。
5. 运行失败显示失败原因和重试入口。

继续使用每秒轮询；本阶段不引入 WebSocket/SSE。轮询必须在运行进入终态后停止，组件卸载时清除计时器。

## 2.5 初稿显示

工作台顶部或生成状态区需要能区分以下状态：

- `正在生成素材`
- `正在导出初稿`
- `初稿已完成`
- `生成有失败项`
- `有候选待确认`
- `有未导出修改`

初稿完成后提供：

- 初稿视频播放入口。
- 打开导出记录或查看输出文件入口。
- 继续编辑入口。
- 手动导出入口。

初稿完成不是“项目已锁定”。用户可以继续修改项目。

## 2.6 阶段测试

- 主入口创建项目后自动启动运行，不需要第二次点击 `开始生成`。
- 直接生成入口不创建工作台项目。
- 创建成功但启动运行失败时，项目可恢复且可以手动重试。
- 运行中刷新页面，活动运行可恢复并继续轮询。
- TTS 完成后时间线显示真实时长。
- 图片完成后自动填充当前版本或候选版本。
- 单个场景失败不阻止后续场景。
- 运行完成后恰好创建一个初稿 `ExportRevision`。
- API 重启或重复轮询不会重复创建初稿导出。
- 初稿导出期间修改项目，初稿快照和输出不变。
- 初稿导出失败后显示错误并可以基于同一个快照重试。

## 2.7 阶段 2 闸门

- 用户从快捷创作点击一次主按钮即可进入正在生成的工作台。
- 所有场景在生成过程中稳定显示并逐步填充。
- 全部素材成功时自动得到初稿视频。
- 失败、取消、恢复和重复提交行为符合不变量。
- 初稿导出不会重复消耗图片/TTS 生成。

完成后停下来，等待产品负责人确认。

# 阶段 3：P0 工作台编辑闭环

## 3.1 阶段目标

让用户在初稿生成后完成真正的“微调 -> 手动导出”闭环，重点是项目级 BGM、分镜顺序、停留时长、候选确认、未导出状态和导出检查。

本阶段仍不实现完整 NLE，不增加多轨编辑器。

## 3.2 项目级设置

新增一个简洁的项目设置区域，可以放在工作台顶部抽屉或右侧检查器的项目模式中。首期只展示和编辑已存在且导出链路已支持的配置：

- BGM 选择。
- BGM 音量。
- 字幕启用状态和现有字幕样式入口。
- 模板/画布等只读或明确可编辑字段。

配置保存调用阶段 1 的 `PATCH /api/projects/{project_id}`。保存配置时：

- 不触发 AI 素材重新生成。
- 不修改活动 `GenerationRun` 的快照。
- 设置项目为 `dirty=true`。
- 关闭页面前如果存在未导出修改，提示用户。

如果 BGM 是自定义上传，继续使用现有上传大小、类型、项目目录隔离和临时文件清理规则。首期不建设跨项目音乐库。

## 3.3 分镜编辑

继续使用现有 `SceneInspector` 和 `WorkbenchTimeline`，只补齐 P0 行为：

- 旁白自动保存草稿；只有明确点击重新生成配音才创建 TTS 任务。
- 提示词自动保存；只有明确点击重新生成图片才创建图片候选任务。
- 候选版本必须通过 `使用此版本` 才替换当前版本。
- 重新生成或上传不会清除旧版本。
- 顺序保存必须使用完整场景 ID 列表，服务端校验每个项目场景恰好出现一次。
- 停留时长保存必须防抖，不能每个键盘输入都提交一个请求。
- 停留时长不能小于音频时长；服务端是最终校验方。

所有保存操作成功后刷新或合并最新项目状态，不能使用旧响应覆盖用户刚刚完成的另一个修改。

## 3.4 未导出状态

项目需要让用户清楚知道当前编辑结果是否已经导出：

- 没有任何成功导出：显示 `尚未导出`。
- 项目内容与最近成功导出相同：显示 `已导出`。
- 修改分镜、版本、顺序、停留时长或 BGM 后：显示 `有未导出修改`。
- 导出进行中：显示 `导出中`，允许继续编辑，但当前导出使用旧快照。

不要在每次修改后自动导出整片。用户明确点击导出时才创建新的手动 `ExportRevision`。

## 3.5 手动导出

导出面板必须显示：

- 分镜数量。
- 总时长。
- 当前画幅/模板。
- 当前 BGM 和音量。
- 当前版本与候选数量。
- 缺少图片或音频的场景。
- 生成中或失败的任务。
- 是否存在未导出的修改。

默认规则：

- 仍有缺失素材时阻止导出。
- 有候选但未确认时允许导出，并明确说明仍使用当前版本。
- 用户显式选择不完整导出时必须二次确认。
- 提交后保存不可变快照，再启动导出任务。

导出按钮防止重复点击。导出失败保留 `ExportRevision`，提供重试原快照入口。

## 3.6 阶段测试

- 修改 BGM 后项目配置持久化，重新打开项目仍保持。
- 修改 BGM 不创建图片/TTS 任务。
- 修改 BGM 后 `dirty=true`，手动导出后恢复为 `dirty=false`。
- 修改旁白后音频状态变为过期，未点击重新生成前不创建新 TTS。
- 重新生成 TTS 后使用真实新时长更新分镜。
- 修改提示词后图片状态变为过期，未点击重新生成前不创建新图片。
- 新图片保存为候选，当前版本不变。
- 选择候选后当前版本切换，候选列表仍可读取。
- 顺序和停留时长导出到快照且最终视频生效。
- 导出期间编辑项目不会改变正在运行的 `ExportRevision`。
- 导出失败可使用原快照重试。

## 3.7 阶段 3 闸门

- 用户可以在工作台中修改 BGM、顺序、停留时长和素材版本。
- 用户能看懂当前项目是否有未导出修改。
- 手动导出使用编辑后的当前版本和项目配置。
- 导出失败不会丢失项目编辑或快照。
- 直接生成旁路没有被工作台逻辑污染。

完成后停下来，等待产品负责人确认。

# 阶段 4：轻量时间线和预览增强

## 4.1 阶段目标

在 P0 闭环稳定后，把卡片式时间线提升为适合日常微调的轻量单轨时间线，但仍不扩展成完整多轨编辑器。

## 4.2 首期交互

使用现有 React 和浏览器原生能力优先实现：

- 点击场景切换中央预览和右侧检查器。
- 当前场景高亮。
- 当前场景旁白音频播放/暂停。
- 上一个/下一个场景。
- 总时长和当前场景时长显示。
- 时间线水平滚动。
- 分镜顺序拖拽或继续保留明确的左右移动按钮作为无障碍后备操作。
- 通过拖拽或步进控件增加画面停留时间。
- 保持片段最小宽度，避免 0 秒、长旁白和加载状态导致布局跳动。

首期不做任意裁短。用户需要缩短内容时，编辑旁白或语速并重新生成 TTS。

## 4.3 预览策略

不要为了编辑器预览引入 `ffmpeg.wasm`。

推荐按能力分层：

1. 当前场景预览：图片/视频元素 + 当前场景音频。
2. 初稿或最近导出视频：使用现有输出文件进行整片播放。
3. 修改尚未导出时，不承诺浏览器中实时合成完整视频；明确提示“导出后预览最终效果”。

如果必须提供修改后的整片实时预览，先单独进行技术验证，确认性能和编码兼容性后再立项，不在本阶段偷偷引入浏览器端视频合成。

## 4.4 可选的小型依赖评估

只有原生能力无法满足需求时才评估局部依赖：

- 音频波形：可评估 WaveSurfer.js。
- 拖拽排序：先评估原生 Pointer Events/HTML Drag and Drop，确有复杂交互再考虑现有生态组件。
- 程序化预览/渲染：Remotion 只能作为渲染或播放器候选，不能当作完整编辑器。

任何依赖引入必须单独记录：版本、许可证、包体积、浏览器兼容性、是否影响当前 Node/Vite 构建，以及删除依赖后的降级行为。

不要在本阶段接入完整 OpenCut、DesignCombo 或其他编辑器仓库，除非阶段 5 的评估明确证明自有轻量时间线已经无法满足产品需求。

## 4.5 阶段测试

- 30、60、100 个分镜滚动和选择不卡死。
- 时间线片段宽度稳定，加载状态不会导致其他片段位置跳动。
- 顺序拖拽后刷新页面保持一致。
- 当前场景音频播放、暂停和切换不残留旧音频。
- 时长拖拽不会把片段设置到音频时长以下。
- 窄屏下分镜面板和检查器仍可通过抽屉访问。
- 键盘和屏幕阅读器可以访问顺序、选择、播放和导出关键操作。

## 4.6 阶段 4 闸门

- 工作台可以高效完成常见分镜级微调。
- 用户不需要依赖复杂的完整编辑器才能完成 P0 目标。
- 30-100 分镜项目在目标本地浏览器环境下可用。
- 没有为视觉增强引入不必要的媒体处理链路。

完成后停下来，等待产品负责人确认。

# 阶段 5：完整验收、回归和上线准备

## 5.1 阶段目标

对前四个阶段进行端到端验收，确认生成、编辑、导出、恢复和失败场景在真实本地环境中一致，再决定是否上线 P0 或进入完整视频片段/多轨编辑的下一期评估。

## 5.2 后端验收矩阵

### 项目与配置

- 创建 1、30、100 个分镜项目。
- 空标题、空旁白、超出分镜上限被拒绝。
- 配置白名单和并发更新冲突符合约定。
- 项目重启后配置、顺序、版本和 BGM 保持。

### 生成运行

- 全部素材缺失时完整运行。
- 音频有效、图片缺失时只生成图片。
- 图片有效、音频过期时只生成 TTS。
- 旁白变化不触发图片重建。
- 提示词变化不触发音频重建。
- 运行中修改等待场景，当前运行仍使用原始快照。
- 当前场景锁定，其他场景可编辑。
- 单场景失败后续场景继续。
- 暂停、恢复、取消、重启恢复和仅重试失败项。
- 重复点击开始不会创建两个活动运行。

### 导出

- 初稿只创建一次。
- 导出不重复生成 TTS 或图片。
- 候选不自动替换当前版本。
- 导出快照对项目后续修改保持不变。
- BGM、顺序、停留和字幕配置真实进入输出。
- 导出失败可重试且错误可读。
- 不完整导出有明确二次确认和警告。

## 5.3 前端端到端验收

使用 mock provider 或已有测试替身，不触发真实付费生成服务：

1. 用户配置 5 个分镜。
2. 点击 `生成初稿并打开工作台`。
3. 页面进入工作台，显示 5 个占位分镜。
4. 运行过程中其中一个场景失败，其他场景继续填充。
5. 用户修改一个等待中的场景，确认不会覆盖当前运行快照。
6. 运行完成后自动生成初稿或显示失败重试入口。
7. 用户确认一个候选图片，调整一个分镜顺序，延长一个分镜停留，修改 BGM。
8. 导出检查显示当前配置和未导出状态。
9. 点击手动导出，导出快照包含所有修改。
10. 导出期间刷新页面，任务和编辑状态可恢复。
11. 导出成功后打开输出视频，确认时长、顺序、BGM 和素材正确。
12. 回到项目再次修改，确认旧导出仍可访问且项目标记为有未导出修改。

## 5.4 浏览器和本地环境

至少验证：

- 桌面宽屏：三栏工作台、中央预览、右侧检查器和底部时间线不互相遮挡。
- 窄屏：左侧分镜和右侧检查器抽屉可以打开，导出按钮始终可访问。
- 30+ 分镜：列表滚动和时间线横向滚动可用。
- API 重启：活动运行和导出任务恢复。
- 文件路径异常：缺失媒体显示明确错误，不泄露绝对路径。
- FFmpeg 不可用：导出失败状态可读，项目数据不损坏。

## 5.5 是否接入完整开源编辑器的决策闸门

只有 P0 工作台经过真实使用后仍无法满足需求，才评估完整开源编辑器。评估必须做一个最小 PoC，不直接改主分支。

PoC 至少验证：

- 是否支持 React/Vite/Node 当前版本。
- 是否可以接收现有 `Project / Scene / AssetVersion` 数据。
- 是否能导出为现有 `ExportRevision`，而不是创建第二套项目数据库。
- 是否支持本地媒体路径、当前图片 + 音频模型和后端 FFmpeg。
- 是否能保留候选版本、项目配置和失败恢复语义。
- 是否满足 Apache-2.0 项目的许可证和分发要求。
- 引入后的包体积、性能、维护成本是否低于继续扩展当前工作台。

如果 PoC 不能通过，继续扩展当前轻量工作台，不因“已有开源代码”而承担新的架构债务。

## 5.6 最终上线闸门

- P0 验收矩阵全部通过。
- 生成、初稿导出和手动导出均经过真实 FFmpeg 输出检查。
- 关键测试在 CI 或本地标准命令中可重复运行。
- 没有未处理的项目数据迁移、路径安全、媒体清理或许可证问题。
- 产品确认当前“图片 + 旁白 + BGM”的轻量工作台已经满足首批用户。
- 若要支持 MP4 分镜或多轨编辑，单独创建下一期设计，不混入本计划。

完成后停下来，等待产品负责人决定上线、修复遗留问题或进入下一期。

# 7. 给后续编码模型的执行规则

1. 只实现当前阶段，不提前实现后续阶段。
2. 开始编码前先读取当前工作区状态和本计划相关文件。
3. 保留用户已有改动，不使用 `git reset --hard`、`git checkout --` 或其他破坏性回滚命令。
4. 优先复用现有 API、repository、TaskManager、FFmpeg 和工作台组件。
5. 不为一次性使用场景增加抽象层、工厂、配置系统或完整编辑器依赖。
6. 非平凡逻辑必须留下最小可运行测试；优先扩展现有 pytest 和前端状态测试。
7. 所有媒体输入、任务状态、快照和错误都必须可恢复、可诊断。
8. 发现“实际需求是 MP4 分镜”或“需要多轨 NLE”时，立即停在当前阶段闸门，向产品负责人报告，不擅自扩大范围。
9. 每个阶段完成后必须停下来等待确认；用户确认后才开始下一阶段。
